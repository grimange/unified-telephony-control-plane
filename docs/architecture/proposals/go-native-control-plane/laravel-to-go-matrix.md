# Laravel-to-Go responsibility and compatibility matrix

Status: **PROPOSED / architecture inventory and migration design**. Source inspected on 2026-10-21. This document adds no writer, changes no route, and makes no new runtime acceptance claim. The operator-selected target is one Go backend codebase; Laravel remains the current behavioral reference and deployed application implementation during transition.

The [canonical ledger](../../../roadmap/phase-status.md) governs accepted phase and runtime status. CP1–CP6 below are proposed migration stages, not canonical phase completion records. Every new Go owner initially operates in an isolated test or shadow environment; actual authority transfer requires a separately reviewed cutover packet.

## Scope and evidence notation

The inspection covered 249 PHP application files, 63 migration files, 80 PHP files under `apps/api/tests`, all four route files, bootstrap/configuration, and the Vue API/realtime clients. `routes/web.php` contains 110 explicit GET/POST/PATCH/PUT/DELETE declarations; `routes/api.php` contains four GET declarations. Framework registration adds broadcasting authorization separately. Counts are source inventory, not counts of independently accepted features.

Paths in tables are repository relative. PHP class names below resolve beneath the indicated source directory; tests resolve beneath `apps/api/tests`. Tables are durable PostgreSQL authority unless explicitly identified as provider-owned, framework/session state, or a projection. Redis is transient only. The configured Laravel defaults (`SESSION_DRIVER=database`, queue connection `database`) are configuration defaults, not evidence of the deployed drivers. Environment-specific Redis configuration, scheduler locks, broadcasting, throttles, and caches must be checked at a future cutover.

Test names identify existing behavioral oracles; these tests were source inspected, not rerun for this architecture document. Historical live evidence remains evidence of the implementation and environment recorded there, never proof of a future Go implementation.

The retained UI centralizes types/fetch/error behavior in `apps/web/src/api/platform.ts`. It sends same-origin cookies, obtains CSRF via `/auth/csrf`, uses `X-CSRF-TOKEN`, cancels via AbortController, handles JSON error details and disconnects realtime on 401. Preserve its endpoint-by-endpoint payload shape: calls use a `data`/`pagination` envelope; not all other list endpoints share this representation.

`apps/web/src/realtime/runtimeNodeRealtime.ts` uses **Laravel Echo + pusher-js**, broadcaster `reverb`, configured `/app` WebSocket path, and private authentication at `/api/broadcasting/auth`. - `conference.operational-state.changed`
- `runtime-operation.operational-state.changed`
- `runtime-reconciliation.operational-state.changed`

Laravel scheduling invokes outbox, command and event normalization workers every minute with overlap guards; reconciliation is a scheduled callable; stale observation derivation runs every five minutes; placement every minute; recovery-metric pruning hourly. Simulator/provider target setup and telephony expiry/cleanup/failover run every minute. These are source scheduler declarations, not measurements of effective deployment cadence. The future Go scheduler must retain work eligibility/due-time semantics and shutdown behavior, while PostgreSQL leases remain durable worker authority; Redis scheduler mutexes alone cannot transfer ownership.

Framework-level `schedule:run`, queue workers, Reverb, migration and bootstrap commands also contribute runtime responsibilities. `AsteriskConferenceParticipantBindingRetryJob` is a concrete Laravel queue job and can redispatch itself. Drain or explicitly convert its pending work at transfer; Go must not deserialize arbitrary PHP job payloads. Queue/session drivers have configurable Redis and database variants; no generic `jobs`, `job_batches` or `failed_jobs` creation migration was found in this application's migration directory. Do not infer those tables exist merely from queue configuration.

## Schema coverage and migration ownership

The matrix covers all material table families discovered through explicit `Schema::create`, dynamic route-table creation and SQL registrar migration statements. The migration chain additionally alters constraints, catalogs, indexes, views and grants. The future Go migration baseline must preserve **all 63 files' effective schema**, not reconstruct only the create-table statements. `inbound_routes` and `outbound_routes` are created through a loop and must not disappear from automated schema inventories. Provider tables/views and framework session state need explicit ownership even when not ordinary domain repositories.

No schema ownership transfer occurs here. CP1 must use a disposable database built from the existing migrations, compare schema/constraints and exercise Go persistence against it. A later migration-authority boundary must freeze the Laravel migration ledger, adopt its complete resulting schema once, and name the sole tool permitted to apply forward migrations. Shared database read compatibility never implies permission for concurrent PHP and Go writes.
